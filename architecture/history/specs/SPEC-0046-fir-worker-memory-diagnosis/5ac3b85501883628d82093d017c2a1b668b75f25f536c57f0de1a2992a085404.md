# FIR 實際記憶體用量優化與移除預估阻擋

## Problem
使用者明確澄清：要修改的是優化實際使用量；可以不計算預估值，也不需要使用預估值作保護。當初因為實際用量過高才提出需求。先前的估算數字診斷只提供配置線索，不能取代降低實際配置與實測驗收。
提供的 FIR 診斷為單一 worker，最壞 fold 有 2,070,704 training rows、33 taps、3 channels。matrix_construction 10.691 GB、fit 5.549 GB 是歷史估算而非實測；不能作本次修改成果或未來保護依據。

## Solution
已採用目標為降低 FIR 實際記憶體用量，並讓生產訓練流程停止計算與使用預估值作啟動阻擋。共用 FIR/MLP 訓練估算入口與 UI 會受影響；MLP 訓練數學不在本次優化目標。
候選實作採用有界分塊的 FIR 特徵建立、統計／Ridge 累積、robust refit、校準及評分，避免保留完整的樣本數乘 History 特徵矩陣；若共享的矩陣入口仍供 MLP 使用，直接配置連續陣列以消除 scalar/list 暫存。保留資料、History、通道順序、float64 訓練與既有模型／判定契約。
保留現有基於實際系統記憶體讀值的 90% 執行中 ceiling、MemoryError/OS 記憶體錯誤終止、取消、子程序回收與零重試；預估保護的移除不代表移除這些現有行為。
取消 Auto／Manual 模式切換；介面直接選擇 1–8 個 worker，沿用既有手動預設值 1。執行時數量最多為可執行 jobs 數，執行中鎖定設定，設定仍不持久化。預設單 worker 讓 jobs 依序完成；使用者可自行提高並行數，實際用量也會增加。

## User Stories
使用者需要在保留資料與模型行為的前提下降低 FIR 實際尖峰及常駐用量，訓練不再被推算的預算拒絕。

## Discussion Context
### DISC-001: 修正為實際用量優化
- **Situation:** 前幾輪根據使用者附件拆解介面估算，指出 list/scalar 暫存，但沒有修改產品。
- **Question:** 使用者主動澄清原始修改目標與預估保護用途，非 assistant 新提問。
- **Options and tradeoffs:** 僅調整估算不會降低配置；候選分塊實作需要以原有數值容差與實測峰值驗證。
- **User answer:** 要修改的是優化實際使用量。可以不用計算預估值，也不需要使用預估值作保護。當初是因為記憶體用量過高，才提出這個需求。
- **Explicit rationale:** 實際用量過高才是原需求。
- **Resulting impact:** DEC-001、DEC-002 與 REQ-001、REQ-002。先前 6.33 GB 的條件式估算不能成為成果或驗收；驗收改為實測。分塊處理是候選實作方向，尚未由使用者確認完整方案。Source: user-actual-memory-optimization-20261012。

### DISC-002: 移除 Auto
- **Situation:** 取消估算後原 Auto 的 worker 數決策來源消失，需要決定介面行為。
- **Question:** Q-001@5：取消記憶體預估後，Auto 的 worker 數希望如何決定？我建議固定 1 個以降低實際用量，並保留 Manual 1–8；代價是多個工作依序完成，訓練時間可能增加。
- **Options and tradeoffs:** 提議保留 Auto 固定 1；使用者選擇直接移除 Auto。手動提高 worker 仍會增加實際配置，預設 1 的多 jobs 訓練需依序完成。
- **User answer:** 可以不需要有Auto
- **Explicit rationale:** 使用者未另提供理由；不推定其他動機。
- **Resulting impact:** DEC-003、REQ-005、AC-004；移除模式切換，直接選擇 1–8，沿用既有手動預設 1。Source: user-remove-auto-20261012。
