# Dual-IMU Collision Studio UI

## Problem

The algorithm discussion was completed in Codex task `01a01da3-a65d-7800-99af-43a8b9d3ade1` while working in the firmware repository. The standalone Python tool now needs a concrete, modern UI contract in this project without losing the algorithm, annotation, validation, and data-partition decisions already made.

## Solution

Design a modern standalone Python/PySide6/Qt Quick/QML desktop UI around a guided single-session workflow: import and allocate data, annotate, train, replay and qualify, then export the selected profile. Use one main window with persistent left-side stage navigation and a central stage workspace; the annotation stage can enter a focus mode that collapses nonessential navigation and panels. Use a light professional visual language with white and light-gray surfaces, dark text, restrained blue accents, and accessible high-contrast plot and state colors. Source files are read in place and workflow state is not saved as a recoverable project. Users may return to completed stages during the session, but changing upstream inputs shall visibly invalidate dependent downstream results. The application shall be newly implemented in this repository while following the local WaveInsight project's Python-to-PySide6-to-QML layering and design language; it shall not import, link to, or require the WaveInsight project at runtime. Engineering traces shall use a custom scene-graph `QQuickItem` fed with viewport-bounded decimated data, while editable annotation regions and handles shall use QML overlays.

## User Stories

- As an annotator, I can inspect and correct proposed cycle/event intervals directly on waveforms.
- As an analyst, I can train and compare candidate FIR residual models without contaminating held-out test data.
- As a validator, I can inspect collision events, false events, latency bounds, exclusions, and evidence sufficiency.
- As a firmware developer, I can export the selected immutable detector profile.
- As a user, I can work in a coherent modern interface whose hierarchy and state are immediately understandable.

| REQ-016 | For each Training round and each sample-rate, FIR-history, Ridge-alpha, residual-scale, K, score-mode, and confirmation-mode candidate, every cross-validation fold and final fit shall produce per-sample residual scores only from eligible `Normal Robot Motion` evidence at or above that round's active minimum Robot Speed. For each requested physical history `H` in exactly `{4, 8, 16, 32}` ms and confirmed Sample Rate `fs` Hz, the causal tap count shall be `L = floor(H * fs / 1000) + 1`, using lag indices `0..L-1` so the current sample is included and `effective_history_ms = 1000 * (L-1) / fs <= H`. Within each cross-validation fold, every FIR input feature shall be standardized using mean and population standard deviation computed only from that fold's fitting rows; held-out rows shall use those unchanged fit-derived values. Ridge shall minimize mean squared prediction error plus `alpha * squared_l2_weight_norm` in standardized feature space. After model selection, final fitting shall recompute feature standardization from all eligible active-range Normal Robot Motion fitting rows, perform the declared initial fit and robust refit, and algebraically transform weights and biases back to the unchanged source IMU scale before replay or export. For each output residual axis, the `STD` candidate shall use `center = mean(r)` and `scale = sqrt(mean((r-center)^2))`; the `MAD` candidate shall use `center = median(r)` and `scale = [REDACTED: personal data] * median(abs(r-center))`. Means and Standard Deviations shall use population denominators over the eligible fitting residual rows. For each axis, define `degenerate_limit = 64 * machine_epsilon_for_the_fit_float_type * max(1, max(abs(r)))`; if center or scale is non-finite, or `scale <= degenerate_limit`, that fold/candidate and any dependent final candidate shall be ineligible with exact axis, estimator, value, limit, fold/fit, and source provenance. No scale floor shall be substituted and no axis shall be omitted. The declared score-mode grid shall contain exactly `MAX_ABS` and `L2_NORM`; the confirmation-mode grid shall contain exactly `1_OF_1`, `2_CONSECUTIVE`, and `2_OF_3`; and each score/confirmation combination shall independently evaluate the inclusive normalized threshold grid 2.00 through 12.00 in 0.25 increments. Samples above a fold- or final-fit cutoff shall seed contamination intervals. A fitting row shall be rejected only when its output sample or any causal FIR input tap overlaps a seeded sample; adjacent affected rows shall merge naturally rather than being expanded to a fixed 50 ms block. If affected rows exceed 5% of eligible rows for that fit, only the worst-scoring 5% shall be rejected deterministically. Each fold fit and final candidate fit shall perform one initial fit and exactly one robust refit, and automatic rejection shall never alter source annotations or create `Ignore` truth. |

## Decisions

| ID | Decision | Rationale |
|---|---|---|
| DEC-001 | Train offline; use immutable parameters during inference. | Keeps runtime deterministic. |
| DEC-002 | Treat residual as unexplained fork motion, not collision truth. | Residual also contains noise and model error. |
| DEC-003 | Complete the standalone algorithm/tool before firmware integration. | Avoids premature coupling. |
| DEC-004 | Produce collision/non-collision output; PICK/PUT are non-collision. | Matches the operational decision. |
| DEC-005 | Consume upstream nearest-timestamp IMU pairs. | Pairing is outside this tool's algorithm scope. |
| DEC-006 | Train independent profiles per sample rate. | Time and residual statistics vary by rate. |
| DEC-007 | Compare 4/8/16/32 ms FIR histories. | Fixed tap count is not portable across rates. |
| DEC-008 | Use A as normal model/scale data, B PICK/PUT as hard negatives, and C collision as positives. | Prevents label-role contamination. |
| DEC-009 | Use Ridge fitting, bounded robust rejection, and exactly one refit. | Provides controlled robustness. |
| DEC-010 | Compare standard-deviation and MAD residual scales. | The tradeoff is empirical. |
| DEC-011 | Compare bounded trigger-confirmation candidates subject to 50 ms latency. | Evidence selects the rule. |
| DEC-012 | Treat initial B/C files as run-level labels without trustworthy event timestamps. | Matches source-data limitations. |
| DEC-013 | Never treat detector peaks or proposals as automatic ground truth. | Avoids circular labeling. |
| DEC-014 | Use user-confirmed post-import annotations and causal replay. | Enables event-level evaluation. |
| DEC-015 | Automatically propose every cycle start before user confirmation. | Reduces repetitive annotation work. |
| DEC-016 | Use fixed event phase proposals with variable event presence/count and auditable exclusions. | Matches repeated process behavior. |
| DEC-017 | Give `IGNORE` global semantics across fitting, tuning, and evaluation. | Prevents accidental reuse and leakage. |
| DEC-018 | Use a separate waveform-only annotation screen with mouse zoom/pan, two-cycle default width, and direct interval editing for recordings of up to about ten cycles. | Small cycle counts favor direct manipulation. |
| DEC-019 | Use a full 3-by-3 MIMO FIR without mandatory coordinate calibration. | Absorbs mounting rotation and cross-axis coupling. |
| DEC-020 | Compare K=4/6/8 median-plus-MAD rejection cutoffs, cap rejection at 5%, and refit once. | Adapts to sparse contamination without erasing normal data. |
| DEC-021 | Latch after collision and re-arm only after score remains below 50% threshold for 50 ms. | Suppresses duplicate events from ringing. |
| DEC-022 | Require zero B-development false events before maximizing C-development recall. | Prioritizes false-stop avoidance. |
| DEC-023 | Show both native normalized score/threshold and collision ratio with 1.0 as the ratio boundary. | Preserves statistical meaning and readability. |
| DEC-024 | Search normalized thresholds from 2.00 to 12.00 in 0.25 steps and warn on boundary selection. | Makes search reproducible and range failures visible. |
| DEC-025 | Store onset truth as `[t_early, t_late]` and report bounded latency. | Preserves annotation uncertainty. |
| DEC-026 | Withhold formal pass until the held-out evidence gate and performance targets are met. | Avoids overclaiming from exploratory data. |

- **Explicit rationale:** The changed Training pool can produce a kernel with different low-speed capability, so the complete remaining range must be tested again.
- **Resulting impact:** DEC-118 closes OD-057 and refines REQ-017, REQ-018, REQ-020, REQ-025, AC-026, and AC-046. Opens OD-058 for deterministic handling when multiple Offsets are simultaneously undetectable at every speed.

### DISC-094: Multiple simultaneously undetectable Offsets
- **Situation:** More than one active Collision Offset can fail collision detection at every supplied speed under the same frozen common kernel. Excluding all of them at once may discard an Offset that a refitted model could recover after only the smallest, most difficult Offset is removed.
- **Question:** Should all completely undetectable Offsets be excluded together, or should the outer fallback exclude one and retrain before evaluating the others again?
- **Options and tradeoffs:** One-at-a-time smallest-first exclusion runs more Learning rounds but preserves the greatest opportunity for Offset coverage recovery and is deterministic. Simultaneous exclusion is faster but can permanently remove more conditions than necessary.
- **User answer:** Select Option 1: exclude one Offset at a time, beginning with the smallest completely undetectable Offset.
- **Explicit rationale:** Retraining after each exclusion allows the remaining Offsets to be reconsidered under the changed common kernel instead of assuming their prior failure is permanent.
- **Resulting impact:** DEC-119 closes OD-058 and refines REQ-017, REQ-018, REQ-020, REQ-025, AC-026, and AC-046. Opens OD-059 to define final ranking between retained winners that cover different Offset and speed ranges.

### DISC-095: User choice across Offset/speed coverage tradeoffs
- **Situation:** Retained kernels can be incomparable: one may cover smaller Collision Offsets but only higher Robot Speeds, while another may cover a narrower Offset set but a wider speed interval.
- **Question:** Should the tool impose an Offset-first or speed-first winner, or expose the kernels and let the user choose?
- **Options and tradeoffs:** Automatic ranking creates one deterministic winner but embeds an operational preference that may not match deployment. Explicit choice preserves the tradeoff and requires a clear comparison UI plus a decision before Profile output.
- **User answer:** Leave the decision to the user; output the kernels as results and show each kernel's covered Offset values and speed interval.
- **Explicit rationale:** Offset and speed coverage are both meaningful, and the user should select the suitable operating envelope rather than having the system impose one dimension.
- **Resulting impact:** DEC-120 closes OD-059 and revises REQ-017 and REQ-020. OD-060 was subsequently answered by DISC-096 and DEC-121.

### DISC-096: Multi-selection with separate Profile headers
- **Situation:** The result page can display several qualified kernels with different Offset/speed operating envelopes, and the user may want to retain more than one without combining their constants or selection policy.
- **Question:** Should the user select exactly one kernel for one header, combine all kernels into one header, or choose any subset and export each as a separate single-Profile header?
- **Options and tradeoffs:** One selected header preserves the smallest output but discards other useful envelopes. One multi-kernel header requires firmware runtime selection. Separate headers preserve independent immutable Profiles and leave integration choice outside the generated code, but require deterministic multi-file naming and overwrite handling.
- **User answer:** Let the user decide which kernels to output and export each chosen kernel as a different Profile header.
- **Explicit rationale:** The user wants multiple useful results available as independent firmware artifacts rather than one forced winner or one combined runtime-switching file.
- **Resulting impact:** DEC-121 closes OD-060 and revises REQ-011, REQ-021, REQ-025, REQ-046, and REQ-049 while preserving one immutable Profile per generated header. Opens OD-061 to define which qualified kernels appear in the selectable results list.

### DISC-097: Selectable kernel result-list scope

### DISC-098: Multi-file destination, filenames, and overwrite behavior

### DISC-099: Explicit kernel qualification metadata in every Profile header
- **Situation:** Each selected retained kernel is exported to an independent Profile header, but firmware integrators need the kernel's model depth and validated operating envelope visible directly in that artifact rather than only in the UI.
- **Question:** Which exact robustness metadata should accompany Kernel Depth, worst in-range Collision Latency, covered Collision Offsets, and qualified speed interval in every header?

- **User answer:** Every header must contain Kernel Depth, Latency, Robustness, and that kernel's covered Offset and speed interval; select Option 2 for Robustness, exporting the combined margin together with false-trigger and collision-detection component margins.
- **Explicit rationale:** The exported Profile must remain self-describing so its complexity, validation timing, robustness, permitted operating conditions, and limiting robustness side are visible where firmware consumes it.
- **Resulting impact:** DEC-124 closes OD-063 and refines REQ-011, REQ-021, REQ-046, REQ-049, AC-039, AC-068, and AC-075. No product decision remains open.

### DISC-100: Diff Accel source interpretation from supplied workbooks
- **Situation:** The supplied `.xlsx` recordings contain Internal Accel XYZ and Diff Accel XYZ columns, no direct External Accel columns, a proposed Header Row 10/Data Start Row 11 layout, and in two files a contiguous trailing region where Diff values have ended while Internal values continue.

Blocking on Internal-only rows after Diff acquisition ends would discard otherwise complete paired data; bounding the effective recording at the last complete paired row preserves those samples but requires an exact visible warning.

- **Resulting impact:** DEC-125 revises REQ-035, REQ-041, AC-036, and AC-062; Header Row/Data Start Row and source mode remain explicitly confirmed per worksheet, complete paired rows enter analysis, contiguous incomplete tails remain visible warnings, and interior gaps remain blocking. ### DISC-101: Whole-recording grouping when only two independent recordings exist
- **Situation:** REQ-026 preferred whole-recording outer validation when multiple independent acquisitions exist, but also required three-to-five folds. Two recordings for one active condition cannot satisfy both constraints simultaneously without splitting a recording or reducing the fold count.
- **Question:** Shall whole-recording independence take priority with adaptive two-to-five folds, shall the strict three-to-five minimum take priority and permit recording leakage, or shall nested inner/outer validation be required?
- **Options and tradeoffs:** Adaptive whole-recording folds preserve acquisition independence and use every supplied recording but provide only two held-out rotations when only two recordings exist. Strict three-to-five Cycle folds keep a uniform fold count but can place Cycles from one recording in both fit and held-out evidence. Nested validation provides additional diagnostics but substantially increases computation and does not provide a unique final-rule selection advantage for the current installed-system calibration scope.
- **User answer:** Option 1: use adaptive whole-recording folds and permit two folds when only two independently acquired recordings are available.
- **Explicit rationale:** Whole-recording evidence should take priority over preserving an arbitrary minimum fold count; current one-recording-per-condition acquisitions remain on the existing three-to-five Cycle-fold path.
- **Resulting impact:** DEC-126 refines REQ-026 and AC-027. Multi-recording hierarchical validation uses two-to-five folds, while all-single-recording validation remains three-to-five folds. No product decision remains open.

### DISC-102: Remove the visible Diff source mode from External IMU mapping

- **Question:** After removing the visible source-mode choice, how shall selected `Diff Accel X/Y/Z` columns be normalized into External IMU axes?
- **Options and tradeoffs:** Automatically applying `External Accel = Diff Accel - Internal Accel` preserves the confirmed workbook semantics with a simpler UI, but makes the transform inferred from exact source-column identity. Treating the selected values as direct External Accel makes the UI completely generic, but would change the meaning of the supplied workbooks and contradict DISC-100 unless those workbooks are modified externally.
- **User answer:** The fourth wizard step shall match `Map Internal IMU axes`; it shall be `Map External IMU axes` and shall not expose a Diff mode.
- **Explicit rationale:** External-axis mapping should use the same direct X/Y/Z interaction pattern as Internal-axis mapping without asking the user to choose an acquisition-source mode. The user selected Option 2 and accepts modifying source Excel workbooks so the mapped columns contain true External Accel values.
- **Resulting impact:** DEC-127 supersedes the source-mode and transformation behavior of DEC-125, revises REQ-035, REQ-041, AC-036, and AC-062, and closes OD-064. The application performs no Diff-minus-Internal calculation and no product decision remains open.

### DISC-103: Same-speed cross-recording annotation proposals
- **Situation:** Annotate & Classify currently exposes no recording switcher, implements no event-template projection, and permanently emphasizes `Confirm Annotation Set`; failed all-recording confirmation reports its blocker only in the footer. The existing contract limits reusable event templates to one recording.
- **Question:** Should one clearly annotated reference Cycle project relative-time Pick/Put/Fork Collision proposals only within its recording, across recordings at the same Robot Speed, or across all speeds?
- **Options and tradeoffs:** Same-speed sharing reuses labels across different Collision Offsets while avoiding unsupported cross-speed phase assumptions; recording-local sharing is safest but repeats work for each Offset; all-speed sharing is fastest but risks phase error when motion speed changes.
- **User answer:** `1` — use recordings with the same Robot Speed.
- **Explicit rationale:** The user wants to switch to a waveform where events are easy to identify and then use relative timing to recognize the corresponding events in recordings at the same speed.
- **Resulting impact:** DEC-128 revises REQ-033/REQ-034 and AC-034/AC-035; REQ-050, DEC-129, and AC-077 capture recording navigation and actionable confirmation feedback. OD-065 remains open for how a completed Cycle becomes or replaces the speed group's active reference template.

### DISC-104: Explicit template activation

- **Question:** Should the first complete Cycle activate automatically, should completion open a confirmation dialog, or should the user explicitly invoke `Use as Reference`?
- **Options and tradeoffs:** An explicit action is safest and least disruptive but adds one click; automatic activation is fastest but may propagate an unintended Cycle; a completion dialog is explicit but interrupts repeated annotation work.

### DISC-105: Optional event classes in a Cycle template
- **Situation:** The current contract requires at least one Pick, one Put, and one Fork Collision in every reference Cycle, but a valid repeated Robot path can contain `Pick=1`, `Put=0`, and `Fork Collision=1` or omit another individual event class.
- **Question:** Which event classes must be present before a Cycle can be used as the same-speed reference template?

- **User answer:** Any one of the events being present is sufficient.
- **Explicit rationale:** The user requires event-class cardinality to follow the actual Robot path rather than a globally mandatory Pick/Put/Collision set.
- **Resulting impact:** DEC-131 revises REQ-033/REQ-034 and AC-034/AC-035/AC-078 so each class count may be zero, the total event count must be positive, zero-count classes generate no proposals, and every valid Cycle in the speed group must match the reference tuple exactly.

### DISC-106: Ignore reference behavior and reason-modal consistency

- **Explicit rationale:** The annotation workflow should apply the same known exclusion timing across equivalent-speed repetitions without silently crossing speed conditions, and it should not expose a locale-dependent or visually inconsistent modal.

### DISC-107: Reference Cycle provisional labels disappear
- **Situation:** A deterministic domain reproduction confirms that clicking `Use as Reference` on a Cycle whose Pick, Put, Fork Collision, or Ignore intervals are provisional removes those intervals from the source Cycle. The current GUI stdout/stderr logs are empty and therefore cannot reconstruct individual clicks.
- **Question:** When the selected reference Cycle contains provisional intervals, shall `Use as Reference` confirm those source intervals, preserve them as provisional, or remain disabled until they are confirmed by another action?
- **Options and tradeoffs:** Confirming the selected source intervals makes the explicit reference action establish durable truth and avoids later source loss, but broadens the action's meaning; preserving them as provisional keeps confirmation separate but allows an authoritative template to originate from unconfirmed labels and complicates provenance; disabling the action until separate confirmation is safest but adds friction and can dead-end the current confirm-all workflow.
- **User answer:** Option 1: `Use as Reference` simultaneously confirms the selected source Cycle and its contained labels.
- **Explicit rationale:** After understanding the same-recording reference flow and cross-recording Anchor flow, the user selected the continuous one-action reference workflow.
- **Resulting impact:** DEC-135 revises REQ-034 and AC-078, preserves source interval identity/visibility, closes OD-067, and completes the product decisions for this revision.

### DISC-108: Destination recordings have no selectable Cycle

- **User answer:** Option 2: manually mark one Anchor Cycle in each same-speed destination recording, then automatically generate the remaining Cycles and project the inner labels.
- **Explicit rationale:** The user selected the anchor-based workflow after observing that the current destination recording contains no Cycle that can be selected.
- **Resulting impact:** DEC-134 revises REQ-033/REQ-034 and AC-034/AC-078; OD-068 is closed and OD-067 resumes as the remaining source-Cycle confirmation-state decision.

### DISC-110: Direct interval drag fails after switching recording

- **User answer:** After switching recording, directly press and drag the event interval. During dragging the interval follows the pointer; after left-button release it jumps an additional distance in the same direction.
- **Explicit rationale:** These are the actual operations and visible results that reproduce both the intermittent disappearance and the release-position error.
- **Resulting impact:** DEC-137 refines REQ-013 and AC-013/AC-077. The repair preserves one-gesture selection and movement, clears preview before model publication, applies displacement exactly once, keeps all synchronized overlays visible, and adds regression seams for recording-switch and release event ordering.
